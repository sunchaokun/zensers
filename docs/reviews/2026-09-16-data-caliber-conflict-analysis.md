## 1. 核心结论

本次暴露的首要问题不是“万台”和“亿台”的单位差异，也不是“全球”和“中国”同时出现。

真正的问题是：报告级 `DataRegistry` 使用过于粗粒度的指标名作为冲突身份，未把地域、期间、统计对象和必要的单位口径纳入同一数据项的身份。因此，系统可能把不同口径的数据错误判定为冲突，进而触发 L5 未解决冲突和低分结果。

本次 E2E 中出现的：

- 中国市场出货量：6904 万台
- 全球市场出货量：2.985 亿台

在地域和统计范围不同的情况下，不应直接判定为冲突。它们最多是两个需要分别标注口径的数据项。

## 2. 问题分类

### 2.1 不属于数据冲突的情况

以下情况本身不能判定为冲突：

1. 单位不同但数值可转换，例如 `6904 万台` 与 `0.6904 亿台`。
2. 地域不同，例如中国市场与全球市场。
3. 期间不同，例如 2025 年全年与 2026 年 Q1。
4. 统计对象不同，例如智能手机总市场与高端智能手机市场。
5. 来源不同但数值一致或差异在允许误差内。
6. 来源 URL 缺失，但指标、数值和来源名称仍然存在。

### 2.2 应当判定为真实冲突的情况

只有在以下核心口径一致时，数值不一致才应进入冲突流程：

```text
规范化指标
+ 单位/可转换单位
+ geographic_scope
+ period
+ population 或 statistical_object
+ 必要时的 caliber / market_segment
```

例如：

```text
市场出货量 + 中国 + 2026Q1 + 中国智能手机市场
```

同时出现两个不能解释的值，才是同口径数据冲突。

### 2.3 来源信息质量问题

`source_url` 缺失、证据 ID 不完整、来源名称过于模糊，属于可追溯性和质量等级问题，不应自动等价为数值冲突。

建议分开记录：

- `data_conflict`：同口径数值矛盾
- `evidence_incomplete`：来源或证据字段不完整
- `scope_metadata_missing`：口径字段缺失
- `scope_mismatch`：不同口径，正常隔离

## 3. 代码证据

### 3.1 报告级注册器的关键缺陷

文件：`src/agents/fixed_agents/report_upgrade/data_registry.py`

当前注册器的 `_normalize_metric()` 主要按指标文本建立 key。`register()` 在 key 已存在时，直接比较已有值和新值；虽然保存了部分证据字段，但这些字段没有参与指标身份判定。

结果是：

```text
normalize("出货量") = "出货量"
normalize("出货量") = "出货量"
```

中国、全球、不同期间或不同统计对象的数据可能进入同一个冲突桶。

### 3.2 另一套 canonical registry 与报告 registry 不一致

文件：`src/core/data/canonical_registry.py`

该注册器已经尝试将 `period`、`geographic_scope`、`population`、`unit`、证据身份等字段纳入 key。但报告生成实际使用的 `report_upgrade.DataRegistry` 并没有完整复用这一身份规则。

这形成两套数据身份体系：

1. 执行阶段 canonical registry：较细口径。
2. 报告阶段 DataRegistry：主要按指标名聚合。

同一份数据在执行阶段可能被正确区分，进入报告阶段后又被错误合并。

### 3.3 报告 agent 的输入边界不足

文件：`src/agents/fixed_agents/report_upgrade/orchestrator.py`

`_extract_chapter_data()` 当前主要按章节、父章节、子章节和内容依赖筛选数据，没有对 `geographic_scope`、`period`、`population` 做强制过滤。

同时，章节 prompt 还可以收到全局原始证据池和完整原始缓存。这样报告 agent 可以看到其他章节、其他地域和其他期间的数据，但没有一个机器强制的数据边界。

### 3.4 当前 L4 检测属于事后文本扫描

文件：`src/agents/fixed_agents/report_upgrade/defense_audit.py`

当前 `scope_collision` 主要根据同一段文字是否同时出现“全球/世界”和“中国/国内”，再结合“市场/销量/增速”等关键词进行判断。

该检查有两个局限：

1. 它不能判断两个数字是否绑定到同一数据点。
2. 它不能判断“全球基准与中国市场对比”是否是有意且明确的比较。

因此它既可能漏掉真实的口径混用，也可能把合法的对比表述误判为冲突。

## 5. 根因树

```text
最终出现“数据冲突”
├─ 报告 DataRegistry 以指标名为主要 key
│  └─ 未将地域/期间/统计对象作为身份
├─ 执行 registry 与报告 registry 不是同一套身份规则
├─ 章节数据提取不按口径过滤
│  └─ 全局证据池可进入任意章节 prompt
├─ 报告 agent 输出允许正文与数据点脱钩
└─ L4/L5 主要事后判断
   └─ 无法区分真实冲突、正常比较和来源字段缺失
```

## 6. 建议修订方案

### 6.1 第一优先级：统一数据身份

建立唯一的 `DataIdentity`，至少包含：

```text
metric_normalized
unit_normalized
geographic_scope_normalized
period_normalized
population_normalized
statistical_object_normalized
caliber_normalized
market_segment_normalized
```

报告 registry 和执行阶段 canonical registry 都使用同一套 key 生成规则。

### 6.2 第二优先级：冲突只在同身份内比较

注册流程应遵循：

1. 先规范化单位，不因“万台/亿台”文本差异产生冲突。
2. 先比较地域、期间、统计对象和细分市场。
3. 身份不同则分别保存，不进入 conflict list。
4. 身份相同才比较数值差异和来源权威性。
5. 冲突记录中必须保存完整的两侧口径，禁止只显示指标名和值。

### 6.3 第三优先级：报告章节输入边界

每个章节 manifest 应明确声明：

```text
claim_scope:
  geographic_scope: 中国
  period: 2026Q1
  population: 中国智能手机市场
```

传给报告 agent 的 `chapter_data` 和 `upstream_data_points` 必须优先使用该范围的数据。全局证据池只能作为检索候选，不能直接作为无边界事实输入。

### 6.4 第四优先级：正文断言与数据点绑定

对正文中的定量断言，必须绑定：

```text
claim_id
data_point_id
geographic_scope
period
population
```

没有数据点的定量断言应删除、改为定性表达，或标记为推断；不能仅依赖段落正则判断。

### 6.5 第五优先级：重新分级质量问题

建议将审计结果分为：

- P0/P1：同口径数值冲突、错误覆盖 canonical value、正文用全球值推导中国结论。
- P2：章节口径字段缺失、正文断言未绑定数据点。
- P3：source_url、evidence_id 等来源信息不完整但数值尚未发现矛盾。

质量门禁仍然只负责打分和记录，不阻断报告交付；但正式状态和诊断状态必须准确反映上述差异。

## 7. 不建议的修订方式

以下做法不能解决根因：

1. 仅修改 L4 正则，放宽“全球+中国”判断。
2. 仅把 L5 conflict 改成 warning。
3. 仅统一显示单位，不修复数据身份。
4. 仅让报告 agent 在 prompt 中“注意口径”。
5. 仅补充 source_url，而不补充地域、期间和统计对象。
6. 只在 HTML 输出阶段删除冲突提示。

这些方式最多降低表面告警，不能防止错误数据合并。

## 8. 验收标准

代码修订前后必须至少验证以下场景：

1. 中国 `6904 万台` 与全球 `2.985 亿台`：不产生冲突，分别保留地域。

## 11. 高阶问题：研究深度不足才是核心质量问题

### 11.1 本次 E2E 的深度判断

本次报告虽然完成了 6 个章节、生成了 HTML，且没有出现空章节，但“章节存在”不等于“研究完成”。从实际缓存内容可以观察到：

- 多个章节以行业常识和趋势描述为主。
- 章节正文中反复出现“高端化”“生态竞争”“结构性增长”等抽象判断，但没有形成可验证的因果链。
- 数据支撑主要是指标罗列，缺少变化率、份额迁移、贡献度、相关性或情景计算。
- 对竞争格局的描述没有进一步回答“为什么发生”“谁受益”“持续多久”“什么条件下会反转”。
- 风险提示多为通用风险，没有对应触发条件、可观测指标和行动建议。
- 质量循环主要修复格式、证据字段和局部表述，没有把描述性内容升级为解释性或决策性分析。

因此，本次 E2E 的主要缺陷不是章节缺失，而是：

> 报告完成了信息整理，却没有完成研究判断。

### 11.2 研究深度的分层标准

建议将研究深度明确分为五层，而不是只用章节数量和字数评价。以下是系统内部评估维度，不是要求原样输出到报告中的栏目：

| 层级 | 必须回答的问题 | 当前状态 |
| --- | --- | --- |
| L1 事实 | 发生了什么？数据是什么？ | 基本具备 |
| L2 描述 | 哪些趋势、差异和结构变化？ | 部分具备 |
| L3 解释 | 为什么发生？驱动因素和传导机制是什么？ | 明显不足 |
| L4 推演 | 如果条件变化，结果如何变化？有哪些情景和反事实？ | 基本缺失 |
| L5 决策 | 对企业/投资者/管理者应采取什么行动？触发条件是什么？ | 基本缺失 |

当前系统的质量检查主要集中在 L1、证据字段、格式契约和少量一致性检查，尚未将 L3-L5 作为报告完成的核心要求。

## 12. 深度不足的系统性根因

### 12.1 智能路由按章节拆任务，没有按研究问题拆任务

当前路由主要把用户输入拆成“市场数据、竞争格局、产品价格、渠道需求、技术生态、政策趋势”等章节。这解决了任务分发问题，但没有为每个章节生成：

- 核心假设
- 需要验证的机制
- 关键对比组
- 反事实或替代解释
- 结论所需的最小证据集

结果是每个 agent 都能完成“搜集与总结”，但没有被要求完成“验证与解释”。

### 12.2 数据模型保存了事实，没有保存分析关系

当前 data point 主要保存指标、数值、单位、来源、地域和期间，但没有一等字段表达：

- 指标之间的因果关系
- 驱动因素与结果指标的映射
- 同比/环比/份额变化关系
- 假设、证据、结论之间的绑定
- 结论适用边界和反例

没有这些关系，报告 agent 只能把数据点拼成段落，难以生成可审查的推理链。

### 12.3 报告 agent 的职责被定义为“精修”，天然限制深度提升

章节 prompt 明确要求“精修≠重写”，要求保留分析员初稿的核心论点，并主要优化语言、补充来源和修复结构。

这适合编辑润色，不适合深度研究。若上游分析员只提供趋势描述，报告 agent 会忠实地把浅层内容写得更完整，却不会主动重新设计研究问题、计算派生指标或推翻原有假设。

### 12.4 质量循环偏重形式合规，不足以评价分析价值

现有 L1-L5 可以发现章节缺失、数据绑定、证据身份、口径冲突等问题，但不能充分回答：

- 是否存在明确的因果机制？
- 是否至少比较了两个竞争主体或时间区间？
- 是否使用了派生计算而非只复述原始数字？
- 是否验证了替代解释？
- 是否给出了可证伪预测？
- 是否形成了决策动作和触发条件？

形式检查通过，仍可能得到一份“有数据但没有洞察”的报告。

### 12.5 缺少跨章节综合模型

当前摘要/总结主要从各章结论汇总生成。它可以保证章节覆盖，但不一定产生新的综合判断。

真正的综合分析应回答：

```text
市场变化 → 竞争行为 → 产品/价格变化 → 渠道与用户响应
        → 技术/政策约束 → 企业收益与风险
```

当前系统没有强制要求这些章节之间形成传导链，因此章节之间容易并列而非相互解释。

## 13. 深度修订的目标模型

深度修订不应简单增加字数，而应让每个核心结论具备以下结构：

```text
结论
├─ 事实证据：至少两个独立或互补数据点
├─ 变化计算：同比、环比、份额、差额、贡献度或区间
├─ 机制解释：为什么这些事实支持该结论
├─ 对比/反事实：如果没有该驱动，结果可能如何
├─ 边界条件：结论何时不成立
├─ 预测：未来可验证的方向或区间
└─ 决策含义：行动、优先级和触发条件
```

### 13.1 内部研究准备，不是报告模板

核心假设、待验证机制、关键对比组、替代解释和最小证据集，属于研究 agent 在撰写前使用的内部工作台账。它们的作用是帮助分析师避免只做资料汇编，不能直接变成报告中的固定小标题、清单或格式化段落。

专业报告的最终表达应当是自然的行业研究叙事：将数据、政策、供需变化、竞争行为、技术演进和产业环境组织成连贯的判断，并根据证据强弱调整措辞。报告不需要向读者展示内部假设表、证据矩阵或推理流程，除非用户明确要求研究方法说明。

内部工作台账应至少帮助 agent 完成以下工作，但不应原样输出：

1. 明确本章节真正要解释的行业现象，而不是机械复述章节标题。
2. 找出影响该现象的供需、竞争、政策、技术、成本和渠道因素。
3. 判断哪些数据可以支持事实，哪些内容只能作为分析判断或趋势推演。
4. 进行必要的横向比较、时间比较和结构拆分。
5. 检查是否存在更合理的替代解释，避免把相关性写成因果关系。
6. 根据证据强弱决定结论力度、预测范围和风险表述。

最终正文应以“结论—数据与事实—行业机制—影响与趋势—风险边界”的自然结构呈现，不要求每章机械地重复相同段落，也不要求每个章节都强行加入预测或行动建议。不同类型的章节应允许有不同的分析方式：市场章节可以重趋势和结构，竞争章节可以重行为和份额迁移，政策章节可以重制度影响和传导路径，技术章节可以重产业链约束和商业化条件。

数据不足时，应降低断言强度或收窄结论范围，而不是把“假设、反事实、证据集、数据缺口”等内部术语直接写进报告。必要的不确定性应融入风险、边界和趋势判断中，保持专业报告的自然表达。

### 13.2 综合章节的内部生成要求

摘要和总结应在所有分析章节完成后生成，并且不能只是机械复制各章结论。内部生成时应综合判断：

- 统一市场、竞争、产品、渠道、技术和政策的共同主线。
- 指出最重要的 2-3 个驱动因素及其传导路径。
- 给出基准、乐观、谨慎三种情景或明确说明无法构建情景的原因。
- 给出关键监测指标和未来验证节点。
- 将结论转化为优先级明确的行动建议。

## 14. 深度质量门禁建议

新增“研究深度评分”但继续遵循用户确定的非阻断交付原则：评分记录问题、提供警告，不阻止报告输出。

建议评分维度。评分对象是分析成果的解释力和决策价值，不是报告是否出现固定术语或固定段落：

| 维度 | 权重 | 检查内容 |
| --- | ---: | --- |
| 事实覆盖 | 20 | 核心问题是否有数据或明确证据边界 |
| 派生分析 | 20 | 是否存在计算、比较、分解或趋势推导 |
| 因果解释 | 25 | 是否说明驱动因素、机制和传导路径 |
| 反事实/情景 | 15 | 是否检验替代解释并给出条件变化下的结果 |
| 决策价值 | 20 | 是否给出行动、优先级、风险和触发条件 |

建议状态分级：

- 80 分以上：具备决策级研究深度。
- 60-79 分：具备分析级深度，但仍有明显推断缺口。
- 40-59 分：主要是描述性报告。
- 40 分以下：信息汇总不足以支持判断。

该分数必须与数据证据质量分开记录，不能因为 source_url 缺失就直接推断研究深度低，也不能因为数据字段完整就推断分析有深度。

## 15. 深度修订的实施顺序

在用户批准后，建议按以下顺序实施：

1. 先为路由任务增加研究问题、假设和证据需求，而非只生成章节名。
2. 再为 data point 增加 claim/driver/comparison 等分析关系。
3. 增加派生计算和可审查的分析中间结果。
4. 将“章节精修”拆成“事实校验、机制分析、深度重写”三个职责阶段。
5. 最后让摘要/总结基于全章分析中间结果生成，而不是只读取章节结论。
6. 用小规模固定样本验证，再运行完整 E2E。

## 16. 深度问题的验收标准

代码修订后，至少要能通过以下检查：

1. 内部研究准备能够识别每个章节要解释的行业现象，但这些内部字段不直接出现在报告中。
2. 每个核心结论都能在内部追溯到事实、必要的派生计算和合理的行业解释。
3. 报告在适合的地方呈现可复核的同比、环比、份额、差额、区间或结构变化，而不是机械要求每章都套用。
4. 正文能够自然区分事实、分析判断、趋势推演和风险边界，不使用内部流程术语冒充专业分析。
5. 关键结论经过替代解释和口径边界检查，但不要求把内部反事实过程原样展示给读者。
6. 摘要/总结包含跨章节的行业主线，而不是简单拼接章节结论。
7. 风险提示围绕本章具体结论展开，包含有意义的不确定性和观察方向，而不是通用风险清单。
8. 研究深度分数与来源完整性分数分离记录。
9. 深度不足时报告仍可交付，但必须显示 `available_with_warnings` 和具体深度缺口。
10. 既不能通过增加套话、重复结论、固定模板或增加字数来伪造深度。

## 17. 本项目真正的设计目标：多 agent 联合形成专家判断

### 17.1 不能把多 agent 等同于多章节写作

本系统引入多 agent 的根本目的，不是把一份报告拆成多个章节后并行撰写，也不是让多个 agent 分别搜集若干数据，再由报告 agent 将结果拼接起来。

真正目标是让多个具有不同观察角度的研究角色围绕同一个行业问题进行交叉分析，最后形成单一、连贯、可论证的专家判断。

如果多 agent 只是：

```text
agent A 搜集市场数据
agent B 搜集竞争数据
agent C 搜集技术数据
agent D 搜集政策数据
report agent 拼接章节
```

那么系统得到的仍然是资料汇编，只是资料来源更多、篇幅更长，并不会自动产生研究深度。

### 17.2 智能手机行业分析应形成完整的传导链

以本项目的智能手机研究为例，真正需要分析的不是“内存涨价多少、芯片涨价多少、手机销量多少”这几个孤立数字，而是形成如下行业判断：

```text
内存、芯片等关键供应商大幅提价
        ↓
手机厂商 BOM 成本和供应链压力上升
        ↓
厂商在不同价格带的成本传导能力不同
        ↓
零售价上涨、配置调整、促销收缩或利润率压缩
        ↓
在中国当前收入预期、消费信心和换机需求环境下
消费者对价格上涨的反应不同
        ↓
中低端需求可能延后或下滑，高端需求可能因品牌粘性而相对稳定
        ↓
品牌份额、产品结构、渠道库存和促销策略发生变化
        ↓
最终影响全年销量、ASP、利润和竞争格局
```

这条链条中的每一步都需要数据、行业环境和专业判断共同支撑。报告的价值在于解释这条链条是否成立、传导强度多大、哪些环节可能被其他因素抵消，以及最终会对行业参与者造成什么影响。

### 17.3 “必然销量下滑”也必须经过论证

在研究表达上，即使行业直觉很强，也不能直接把“成本上涨 + 价格上涨”写成未经论证的绝对结论。

专业分析需要进一步验证：

- 价格上涨是否真正传导到终端零售价，还是由厂商利润和供应商共同吸收。
- 不同价格带的需求价格弹性是否相同。
- 中国消费者是否会延长换机周期，转向更低价位，或选择促销渠道。
- 高端品牌的品牌溢价和生态锁定是否降低需求敏感度。
- 政策刺激、新品周期、补贴或促销是否抵消部分下滑。
- 供应短缺是否同时限制供给，使销量下降表现为供给约束而非纯需求约束。
- 同期宏观经济、房地产、就业、汇率或消费政策是否是替代解释。

因此报告可以在证据充分时形成较强判断，例如“成本冲击大概率通过价格和换机周期压制销量，影响主要集中在中低端市场”，但必须通过多角度证据和机制分析支撑，而不是由单个 agent 或单组数据直接推断。

## 18. 多 agent 应如何协同产生深度

### 18.1 不同 agent 应承担不同分析职责

多 agent 的合理分工应围绕研究问题和行业机制，而不是简单按报告目录分工。例如：

- 供应链 agent：识别内存、芯片、面板、电池等成本冲击的来源、幅度、持续性和传导路径。
- 宏观需求 agent：分析中国收入预期、消费信心、换机周期、可选消费和价格敏感度。
- 产品价格 agent：分析不同价格带、配置变化、ASP、促销和成本传导。
- 竞争策略 agent：分析主要品牌谁能提价、谁会牺牲利润、谁会通过降配或渠道补贴应对。
- 渠道库存 agent：分析零售价格、库存周转、渠道压力和促销反馈。
- 技术与供给 agent：分析芯片、内存供给约束是否造成供给侧减产或产品延迟。
- 政策与环境 agent：分析补贴、消费政策、出口环境和产业政策的抵消或放大作用。
- 交叉审查 agent：专门检查因果链、替代解释、证据冲突和结论强度。

这些 agent 不应各自独立完成一篇“自己的章节”，而应围绕同一个核心问题相互引用、质疑和修正。

### 18.2 应存在跨 agent 的争论和汇合阶段

研究深度来自交叉验证，而不是 agent 数量。系统至少需要形成：

```text
问题定义
  → 多视角取证
  → 共享事实底稿
  → 机制分析
  → 观点冲突与替代解释
  → 综合判断
  → 报告叙事
```

例如供应链 agent 认为涨价将导致销量下降，竞争策略 agent 需要判断厂商是否会通过压缩利润吸收成本，宏观需求 agent 需要估计需求弹性，渠道 agent 需要检查终端价格和库存是否已经验证该判断。只有这些观点汇合后，报告 agent 才能形成有条件、有边界的行业结论。

### 18.3 报告 agent 的职责不是拼接，而是综合论证

报告 agent 不应只接收各 agent 的最终段落并进行文字润色。它应接收：

- 共享且经过口径治理的事实底稿。
- 各 agent 对同一问题的判断和证据。
- 互相冲突的观点及其解决状态。
- 派生计算、情景结果和不确定性。
- 研究团队对结论强度的共识。

然后以专业报告语言完成综合叙事，把供应链、宏观、竞争、产品、渠道和政策因素组织成读者可理解的行业判断。内部分析流程不应直接暴露成模板字段，但其推理成果必须体现在报告的解释力上。

## 19. 深度报告与普通报告的区别

普通报告回答：

```text
市场有多大？主要品牌是谁？芯片价格怎样？政策是什么？
```

深度报告还必须回答：

```text
这些因素如何相互作用？
哪个因素是主因，哪个只是伴随现象？
成本冲击如何传导到价格、销量、利润和份额？
为什么不同品牌、价格带和渠道的影响不同？
这个判断在什么条件下成立，又会被什么因素抵消？
未来应观察哪些数据来验证或推翻判断？
```

因此，深度不能用章节数、字数、数据点数或来源数量替代。深度的核心衡量对象是：

1. 是否形成跨因素的因果解释。
2. 是否从多个专业角度相互验证。
3. 是否识别主因、次因和替代解释。
4. 是否分析不同主体、价格带和场景的异质性。
5. 是否把事实推导为有边界的趋势和行业结论。
6. 是否能让读者据此理解行业变化，而不仅仅是知道若干数据。

## 20. 对后续代码修订的约束

后续修订不能只增加字段、提示词或固定章节模板。必须重点检查：

- 路由是否围绕核心行业问题形成分析协作，而不是只做目录拆分。
- 各 agent 是否共享同一份事实底稿和派生分析结果。
- 是否存在跨 agent 的交叉质询和冲突解决。
- 报告 agent 是否能获得不同视角的完整分析，而不是只获得碎片段落。
- 报告生成是否有足够上下文和模型任务空间完成综合判断。
- 质量检查是否能评价机制解释和决策价值，而不仅是字段完整性。
- 当证据不足时，系统是否降低结论强度，而不是用通用套话填充正文。

任何只让报告看起来“更长、更完整、更规范”，但不能提升上述能力的修改，都不应被视为深度修订。

## 21. 优化重点：数据分析 agent 与报告 agent

### 21.1 现有多 agent 能力不是主要瓶颈

系统已经具备多 agent 分批执行、依赖调度和阶段性汇总能力，可以把市场、竞争、产品、渠道、技术和政策等专项任务分发给不同 agent。

当前问题不在于“有没有 agent”或“能不能分批执行”，而在于：

- 数据分析 agent 的输出仍然接近“搜索结果 + 观点摘要”。
- 报告 agent 接收的主要是章节数据和分析初稿，而不是经过多角度推导的分析成果。
- 多 agent 之间的结果没有充分汇合为共同的行业判断。
- 报告 agent 被要求以编辑精修为主，缺少重新组织论证和提升研究深度的授权。

因此优化不应首先扩充 agent 数量，而应提升这两个 agent 的工作深度和输入输出质量。

### 21.2 数据分析 agent 的目标：从数据整理升级为行业分析

数据分析 agent 不应只回答“找到了什么数据”，而应完成以下转换：

```text
原始资料
  → 可比事实
  → 结构变化
  → 驱动因素
  → 影响机制
  → 主体差异
  → 趋势判断
  → 不确定性边界
```

这里的输出是给后续研究和报告 agent 使用的内部分析成果，不是要求直接以模板形式展示给最终读者。

### 21.3 数据分析 agent 必须增加的能力

#### A. 数据加工能力

分析 agent 应优先完成必要的数据加工，而不是把原始数字原样转述：

- 同比、环比和复合增长率。
- 份额变化、排名变化和集中度变化。
- 价格带迁移、结构占比和增量贡献。
- 成本变化对售价、销量和利润的敏感性分析。
- 不同主体、区域、价格带和时间区间的横向比较。
- 多来源数据的交叉验证和差异解释。

例如，对于“内存、芯片涨价”，分析 agent 不应只列出供应商涨价数据，而应进一步分析其对 BOM 成本、终端售价、厂商毛利、产品配置和销量的可能传导幅度。

#### B. 行业机制分析能力

分析 agent 应把数据放入行业机制中解释：

- 供应端冲击如何传导到厂商成本。
- 厂商通过提价、降配、压缩利润或延后促销如何分担成本。
- 消费者在当前中国经济环境下如何响应价格变化。
- 不同品牌的品牌溢价、用户粘性和生态锁定如何改变需求弹性。
- 渠道库存和促销政策如何放大或缓冲终端价格冲击。
- 芯片和内存供给约束是影响销量，还是同时造成供给不足。

分析 agent 可以在内部保留机制链和推理依据，但最终报告必须将其转化为自然的行业分析文字，而不是输出流程化标签。

#### C. 主体异质性分析能力

行业结论不能默认所有企业、消费者和产品受到相同影响。分析 agent 应主动识别：

- 高端、中端和入门级市场的差异。
- 苹果、华为、小米、OPPO、vivo 等品牌的成本传导能力差异。
- 线上和线下渠道的价格反应差异。
- 存量换机用户与新增购买用户的敏感度差异。
- 供应链议价能力强弱对利润和售价的不同影响。

这类异质性分析是把“行业总量判断”提升为“竞争格局判断”的关键。

#### D. 替代解释和结论强度控制

分析 agent 应检查销量变化是否可能由新品周期、补贴、季节性、宏观消费信心、库存调整或供给约束解释，而不能把所有变化都归因于单一成本因素。

最终可以形成强弱不同的结论：

- 事实明确时，使用确定性表述。
- 机制有证据但仍存在替代解释时，使用“大概率、主要原因、预计”等有边界表述。
- 证据不足时，明确区分行业推断与已验证事实。

### 21.4 报告 agent 的目标：从章节编辑升级为综合研究分析师

报告 agent 不应只对初稿做语言润色，而应在不改变事实的前提下完成二次研究综合：

1. 识别各分析 agent 之间的共同主线。
2. 判断哪些因素是主因、次因和结果变量。
3. 解决不同 agent 的观点冲突。
4. 把分散数据组织为因果和竞争传导链。
5. 根据证据强度调整结论力度。
6. 将分析结果写成自然、连贯、专业的行业报告。

报告 agent 的最终产物不应看起来像多个 agent 的段落拼接，而应像一名资深行业分析师阅读了完整研究底稿后形成的统一判断。

### 21.5 报告 agent 需要接收的不是“章节片段”，而是分析底稿

报告生成阶段的输入应从当前的章节数据/初稿，升级为结构化但不直接暴露给读者的研究底稿，包括：

- 经过口径治理的事实数据。
- 派生指标和计算过程。
- 供应链、需求、竞争、渠道、政策等不同视角的分析结果。
- 各分析 agent 对同一问题的判断。
- 分析结果之间的冲突、支持和未解决部分。
- 结论适用范围、证据强度和不确定性。
- 可用于预测和验证的关键指标。

报告 agent 可以据此自由组织章节，不要求把这些字段逐项写入正文。

### 21.6 推荐的 agent 协同流程

```text
专项数据采集
  → 数据分析 agent：加工、比较、解释
  → 交叉分析：供应链/需求/竞争/渠道/政策互相验证
  → 综合研究底稿：统一事实、机制和结论强度
  → 报告 agent：重组论证和行业叙事
  → 专家级质量审查：深度、逻辑、边界、决策价值
  → HTML/文档输出
```

关键变化是：报告 agent 不应过早启动。应当等待主要分析 agent 的结果汇合后，再进行章节撰写和摘要/总结生成。

### 21.7 以智能手机成本冲击为例的目标输出

低深度写法通常是：

> 内存和芯片价格上涨，手机成本增加，厂商可能提高售价，市场销量可能下降。

目标深度应接近以下逻辑，但最终需要转化为自然报告语言：

> 关键零部件涨价首先抬升中低端机型的 BOM 成本，因为这些产品的单位利润空间更窄、成本吸收能力更弱。若厂商将成本传导至零售价，在中国消费恢复偏弱、换机周期延长的环境下，价格敏感型用户可能推迟换机或转向更低价位，导致中低端销量承压。高端市场则可能因品牌溢价、生态粘性和用户结构不同而表现出更强的价格承受能力，但厂商仍可能通过减少促销、调整配置或压缩利润吸收部分冲击。最终，行业总销量、平均售价、品牌份额和利润的变化方向未必一致，关键取决于成本传导比例、需求弹性、补贴力度和渠道库存水平。

这类结论不是凭空增加复杂术语，而是把供应链、价格、需求、竞争和渠道放入同一个可验证的传导链中。

### 21.8 两个 agent 的质量基准

数据分析 agent 的合格标准：

- 不只输出原始数据，至少完成必要的比较和派生分析。
- 不只描述趋势，能够解释主要驱动因素和传导机制。
- 能识别不同主体、价格带和渠道的差异。
- 能指出替代解释和证据边界。
- 输出可被报告 agent 直接用于综合判断的研究底稿。

报告 agent 的合格标准：

- 不机械拼接不同 agent 的段落。
- 不把相关性直接写成因果关系。
- 不用行业套话替代机制解释。
- 能把多个视角组织成统一的行业主线。
- 能自然表达事实、判断、预测和风险边界。
- 结论能够回答“为什么、影响谁、影响多大、持续多久、什么条件下改变”。

### 21.9 优化优先级

建议按以下优先级实施：

1. 先升级数据分析 agent 的输出内容和分析 prompt，使其产出派生分析、机制解释和主体差异。
2. 再建立跨 agent 的研究底稿汇合层，避免报告 agent 只看到孤立章节。
3. 再升级报告 agent 的任务定义，允许其对分析内容进行综合重构，而不是仅做精修。
4. 增加独立的研究深度审查，评价解释力而非只评价字段完整性。
5. 最后调整 HTML 和其他格式输出，确保深度分析在渲染后不被截断或降级。

不建议首先通过增加章节数量、增加 agent 数量、增加 prompt 长度或提高报告字数来解决深度问题。
