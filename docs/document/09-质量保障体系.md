# 09 — 质量保障体系

> 章节定位：理解系统如何全链路保证研究报告质量——从数据采集的源头验证，到跨 Agent 数据冲突检测，再到报告层面多维度质量评分与自动修复。

---

## 1. 全链路质量保障概览

质量保障贯穿研究任务的每个环节，分为 6 个阶段：

```
用户输入
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 1. 数据采集质量          搜索质量过滤、元数据提取      │
│    源头把关              异常检测、来源可信度分级      │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 2. 冲突检测              SharedMemory 优先级写入     │
│    数据竞争解决           偏差检测、同 caliber 冲突   │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 3. 分析质量              分析质量检查器              │
│    论证质量把关           口径声明检查、风险披露评估   │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 4. 报告生成质量           5 阶段质检流水线            │
│    多维评分+自动修复      章节级评分、全文级检查       │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 5. 内容清洗              模板残留过滤、去重检测      │
│    输出净化              质量门禁 + 自动修复          │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 6. 知识沉淀质量          置信度过滤、溯源追踪        │
│    长期记忆              矛盾检测                     │
└─────────────────────────────────────────────────────┘
```

各阶段均有独立阈值配置，见 `config/content_quality.yaml` 和 `settings.quality`。

## 2. 数据采集质量

### 2.1 搜索质量过滤器 (SearchQualityFilter)

**文件**: `src/core/search_quality_filter.py:184`

在搜索结果进入系统前执行多维度质量评分，低于阈值的结果被过滤。

#### 来源可信度分级

| Tier | 分值 | 示例域名 |
|------|------|---------|
| TIER1_AUTHORITY | 100 | gov.cn, worldbank.org, imf.org |
| TIER2_PROFESSIONAL | 85 | researchreport.cn, mckinsey.com |
| TIER3_REPUTABLE | 70 | caixin.com, bloomberg.com |
| TIER4_GENERAL | 50 | sina.com.cn, zhihu.com |
| TIER5_LOW_QUALITY | 20 | 广告/SEO/营销内容（被过滤） |

#### 质量评分权重

| 维度 | 权重 | 说明 |
|------|------|------|
| 可信度 | 35% | 域名层级分级 |
| 相关性 | 30% | 标题/摘要与查询的语义匹配 |
| 深度 | 25% | 内容长度和结构化程度 |
| 新鲜度 | 10% | 按时间衰减 |

#### 自适应阈值

固定阈值 `40.0`（可配置，最低 30.0）。当固定阈值导致通过率低于 33% 时，自动降至 50 分位值，避免在数据稀疏场景下过度过滤。

#### 低质量模式过滤

`LOW_QUALITY_PATTERNS` 正则集过滤：广告关键词、SEO 堆砌、营销模板、点击引诱标题等。

### 2.2 质量元数据提取器 (QualityMetadataExtractor)

**文件**: `src/core/quality/metadata_extractor.py:82`

从原始采集结果中提取质量元数据，不修改原始数据：

| 提取项 | 方法 | 说明 |
|--------|------|------|
| 质量分 | `_extract_score()` | 从 `quality_score/score/credibility/confidence` 等字段提取，0-1 → 0-100 转换 |
| 数据量 | `_calculate_volume()` | 统计 `results/items/data/records` 列表长度 |
| 来源可信度 | `_extract_sources()` | URL + 标题提取，按域名分级为 tier1/tier2/tier3/unknown |
| 来源类型 | `_judge_source_type()` | 识别 official/news/academic/social 类型 |
| 新鲜度 | `_calculate_freshness()` | 从 `date/published_at/created_at` 字段解析，2024-2026 → 90，2023 → 70，2022 → 50 |

**综合质量分**（line 488）：`coverage(40%) + freshness(20%) + credibility(40%)`

### 2.3 数据采集质量检查器 (DataCollectionQualityChecker)

**文件**: `src/core/quality/checkers.py:220`

| 维度 | 权重 | 计分方式 |
|------|------|---------|
| 数据量 | 30% | 阶梯函数：>=100 → 100; >=50 → 80; >=20 → 60; >=10 → 40; >=5 → 20 |
| 质量分 | 40% | 读取 `quality_metadata.quality_score`，默认 50 |
| 来源可信度 | 30% | 权威关键词（gov/政府/official/统计局）→ 80，非权威 → 30，按比例加权 |

**通过阈值**: `80.0`（可配置，通过 `settings.quality.threshold_data_collection`）

### 2.4 异常数据检测

**文件**: `src/core/search_quality_filter.py:584`

对采集到的数值数据进行合理性检查：

| 指标 | 合理范围 | 单位 |
|------|---------|------|
| 营收 | 1-50000 | 亿 |
| 净利润 | -5000-10000 | 亿 |
| 毛利率 | -50-100 | % |
| 市占率 | 0-100 | % |
| PE | -100-500 | 倍 |
| 负债率 | 0-100 | % |

检测逻辑：
- **越界检测**：超出预定义范围标记异常
- **断崖检测**：同比变化 >50% 标记 warning
- **符号翻转**：净利润由正转负 / 负转正标记 critical

## 3. 冲突检测

### 3.1 SharedMemory 优先级写入

**文件**: `src/core/communication.py:199`

跨 Agent 数据共享的核心冲突检测机制。

#### 来源优先级

| caliber | 优先级 | 典型来源 |
|---------|--------|---------|
| `structured_source` | 100 | 财报、数据库、结构化 API |
| `search_result` | 50 | 网页搜索结果 |
| `llm_inference_factual` | 15 | LLM 陈述事实 |
| `llm_inference` | 10 | LLM 推理结论 |
| `llm_inference_speculative` | 5 | LLM 推测性内容 |

#### 写入流程

```
write_canonical(metric, value, caliber, source)
    │
    ├─ 1. 数值偏差检测
    │     |existing - value| / max(|value|, 0.01) > 5% → 标记 ConflictRecord
    │
    ├─ 2. 优先级裁决
    │     ├─ new_priority > existing_priority → 覆盖写入 ✓
    │     ├─ new_priority < existing_priority → 拒绝写入，保留高优先级值
    │     ├─ 同级 + 同 caliber + 同 source → 静默更新（幂等）
    │     └─ 同级 + 同 caliber + 不同 source → 冲突标记，保留原值
    │
    ├─ 3. 存储
    │     {value, caliber, source, publisher, version, timestamp}
    │     version 自增
    │
    └─ 4. 事件发布
          无冲突 → MessageBus 发布 data.canonical.updated
          有冲突 → MessageBus 发布 data.conflict.detected
```

### 3.2 DataCollector（冲突订阅者）

**文件**: `src/core/orchestrator/execution/data_collector.py:19`

订阅 `data.canonical.updated` / `data.conflict.detected` 事件，聚合规范化数据。维护 `_canonical_data` 字典和 `_conflicts` 列表，用于下批次 Agent 的数据注入。

### 3.3 Agent 层矛盾检测

**文件**: `src/core/agents/generic_agent.py`

两层矛盾检测：

1. **启发式预检**（`_detect_claim_contradiction_precheck()`，line 2027）：基于关键词的矛盾对快速扫描
2. **语义检测**（`_detect_claim_contradiction()`，line 2068）：LLM 结构化输出 `{"contradiction": bool, "type": str, "confidence": 0-1}`

写入 canonical 前的矛盾检测（lines 910-932）：将新 claim 与已有 claim 对比，发现冲突则标记 `data.conflict.detected`。

### 3.4 口径差异检测

`_detect_caliber_differences()` 识别口径差异（调整后/扣非/非经常性）来解释数值冲突，避免误判。

## 4. 认知防御体系（L1-L5 五级矛盾检测）

**文件**: `src/core/agents/generic_agent.py:88-117`

系统内置四套认知策略（fact_driven / inference_driven / forward_looking / assessment_driven），每套策略沿五个层级逐级升级，形成从知识获取到矛盾裁决的完整认知防御链。

### 4.1 认知策略选择

`_infer_cognitive_type()`（line 1995）根据分析维度自动匹配：

| 认知策略 | 匹配维度关键词 | 场景 |
|---------|--------------|------|
| fact_driven | 市场空间、营收、利润、市场份额 | 数据主导的事实分析 |
| inference_driven | 战略意图、竞争策略、技术路线 | 需要逻辑推理的分析 |
| forward_looking | 趋势展望、前景、预测 | 前瞻性预测分析 |
| assessment_driven | 风险评估、风险分析 | 风险评估类分析 |
| 兜底 | 其他 | 默认回退 fact_driven |

### 4.2 L1 — 认知层级天花板

每个策略定义 `dimension_ceiling`（该维度允许的最高认知层级），LLM 提取的 claim 若超出天花板则自动降级。

| 策略 | 天花板 | speculative_word_downgrade | 置信度阈值 |
|------|--------|--------------------------|-----------|
| fact_driven | inferential（最高推断级） | strict | factual: HIGH |
| inference_driven | speculative（最高推测级） | moderate | factual: MEDIUM |
| forward_looking | None（不限） | relaxed | speculative: LOW |
| assessment_driven | None（不限） | relaxed | factual: HIGH, inferential: MEDIUM, speculative: LOW |

强制降级规则（`extract_claims()`, lines 1762-1814）：
1. `confidence:LOW` + 有前提条件 + 标注 factual → 降级至 inferential
2. 语句含推测词（可能/预计/或许...）且标注 factual → 降级至 inferential
3. 维度天花板低于 claim 的 epistemic_level → 强制降至天花板级
4. 特殊维度内置硬编码天花板（如 `strategic_intent` → `speculative`）

### 4.3 L2 — 引用口径门槛

| 策略 | caliber_floor | 同级冲突解决 | speculative 写入策略 |
|------|--------------|-------------|-------------------|
| fact_driven | llm_inference_factual | newer_timestamp | never（拒绝写入） |
| inference_driven | llm_inference_speculative | higher_source_count | with_uncertainty_tag |
| forward_looking | llm_inference_speculative | wider_coverage | with_falsification_condition |
| assessment_driven | llm_inference_speculative | wider_coverage | with_falsification_condition |

控制写入 SharedMemory 的最低 caliber 门槛，低于门槛的声明不进入共享记忆。

### 4.4 L3 — 推理与证伪框架

| 策略 | speculative_policy | reasoning_mode | falsification_requirement | evidence_chain_template |
|------|-------------------|---------------|--------------------------|------------------------|
| fact_driven | reference_only（仅参考） | cross_validation | all_inferential（所有推断需证伪） | 数据 → 发现 → 确认 |
| inference_driven | cautious_use（谨慎使用） | causal_chain | speculative_only | 前提 → 推理 → 结论 |
| forward_looking | open_use（开放使用） | scenario_analysis | all_claims | 信号 → 情景 → 概率 |
| assessment_driven | open_use | risk_scenario | key_risks_only | 风险触发条件 → 传导路径 → 影响评估 → 应对策略 |

每个策略在分析 Prompt 中注入：
- `cross_dimension_instruction`：跨维度交叉验证要求
- `insight_instruction`：个性化洞察发现引导
- 证据链模板约束分析结论的论证结构

### 4.5 L4 — 假设驱动分析

| 策略 | 假设类型 | 数量 | 模板 | 反假设 | Agent 自提假设数 | 验证焦点 |
|------|---------|------|------|-------|---------------|---------|
| fact_driven | 描述性 | 1-2 | 【数据观察H1】→【支持证据】→【确认/否定】→【发现】 | 否 | 0 | Data accuracy |
| inference_driven | 因果性 | 3-5 | 【因果假设H1】→【支持证据】→【确认/修正/推翻】→【结论】 | 是 | 2 | Logic completeness |
| forward_looking | 预测性 | 2-3 | 【预测性假设H1】→【支持信号】→【概率评估】→【情景】 | 是 | 1 | Falsification conditions |
| assessment_driven | 风险情景 | 1-2 | 【风险情景H1】→【触发条件】→【传导路径】→【影响评估】 | 否 | 0 | Scenario plausibility |

假设注入到分析 Prompt，要求 Agent 逐项验证。fact_driven 为"建议探索"，其他策略为"必须验证或修正"。

### 4.6 L5 — 矛盾检测与裁决

**入口**: `_detect_claim_contradiction()`（line 2068），嵌入在 `analyze()` 的 cross_dimension 阶段。

```
新 claim 进入 → L5 预检 → L5 LLM 语义检测 → 矛盾裁决
```

**两阶段检测**：
1. **启发式预检**（`_detect_claim_contradiction_precheck()`, line 2027）：正负面关键词方向检测 + 内容 bigram 重叠度 >0.15 规则，高召回低精度，零延迟
2. **LLM 语义检测**（line 2086）：`{"contradiction": bool, "type": str, "confidence": 0-1}`，`confidence >= 0.6` 确认矛盾

**各策略裁决规则**：

| 策略 | contradiction_resolution | auto_resolve_threshold | escalation_action |
|------|------------------------|----------------------|------------------|
| fact_driven | Data conflict resolution | 0.8 | Flag for human review（标记人工审查） |
| inference_driven | Premise re-examination | 0.6 | Inject as reasoning challenge（注入推理挑战） |
| forward_looking | Scenario reconciliation | 0.4 | Present both scenarios（同时呈现两种情景） |
| assessment_driven | Risk scenario reconciliation | 0.5 | Present both risk scenarios with probability |

矛盾信息注入到后续分析 Prompt 的`已检测到跨维度矛盾（优先处理）`区块，要求 Agent 按 `contradiction_instruction` 处理。


### 7.4 ContentQualityGate

## 8. 自动修复与重试

### 8.1 引擎级重试循环

**文件**: `src/core/orchestrator/execution/engine.py`

#### 阶段质量检查 (`_check_stage_quality()`)

通过条件：`success_rate >= 50%`（`MIN_SUCCESS_RATE = 0.5`）

#### 统一重试 (lines 1563-1593)

```
质量检查失败
    │
    ├─ _identify_failed_agents()
    │   检查基础设施错误 + 质量检查器失败
    │
    ├─ _inject_retry_feedback()
    │   注入 quality_feedback: {score, issues[:5], previous_attempt}
    │
    ├─ 失败 Agent 重置并重新执行
    │
    └─ 最多重试 max_retries 次（从配置读取）
```

#### 检查器选择 (`_select_checker_for_batch()`)

| 条件 | 选用的检查器 |
|------|------------|
| 有 data_points + sources 无 content | DataCollectionQualityChecker |
| 有 content | SemanticQualityAdapter(阈值75) → 降级 AnalysisQualityChecker |
| 有 validation 数据 | DataCollectionQualityChecker |
| 默认 | DataCollectionQualityChecker |

#### 缓存命中质检 (lines 1268-1297)

缓存的 Agent 结果同样需要通过质量检查器。质检失败则重新执行。

### 8.2 Engine 级质量配置

从 `settings.quality` 读取（`engine.py:300-314`）：

| 参数 | 默认值 | 用途 |
|------|--------|------|
| `threshold_data_collection` | 80.0 | DataCollectionQualityChecker 阈值 |
| `threshold_analysis` | 85.0 | AnalysisQualityChecker 阈值 |
| `threshold_report` | 80.0 | ReportQualityChecker 阈值 |
| `max_retries` | 由 config 决定 | 最大重试次数 |

### 8.3 ContentCleaningPipeline

**文件**: `src/core/orchestrator/aggregation/content_quality.py:673`

按序执行的标准清洗管道：

```
1. PromptPatternFilter (line 159)
    移除 LLM 提示痕迹、口语化表达

2. CrossTypeDuplicateDetector (line 231)
    阈值 0.75 相似度，移除重复标题

3. GlobalDuplicateDetector (line 349)
    阈值 0.85，min_length 30
    Jaccard 相似度 + 包含关系检测

4. ContentQualityGate (line 524)
    最终门禁，不可修复项触发生成重试（最多 2 次）
```

### 8.4 M5-a 校准门

**文件**: `src/core/orchestrator/execution/calibration_gate.py:45`

`fix_content_from_canonical()` 在批量执行后执行：

- 用 canonical registry 数据修正报告正文中的数值
- 支持 6 种货币换算：CNY(1.0), HKD(0.92), USD(7.25), EUR(7.85), GBP(9.15), JPY(0.048)
- 检测 canonical 值偏差 >5% 自动修正
- 输出：auto-fixes 计数 + 剩余 conflicts 列表
