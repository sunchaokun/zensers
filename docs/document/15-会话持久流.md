# 15 — 会话持久流

> 章节定位：理解前后端实时通信的核心通道——会话级 SSE 持久流的设计原理、事件体系、消费链路与故障恢复。

---

## 1. 概述

**文件**: `src/core/session_streamer.py` (454 行)

SessionStreamer 是 Zensers 的**会话级实时推送通道**，基于 SSE (Server-Sent Events) 协议，负责将后端所有异步事件实时推送到前端。

与 `ProgressStreamer`（任务级，任务完成后终止）的核心区别：

| 维度 | ProgressStreamer | SessionStreamer |
|------|-----------------|----------------|
| **作用域** | 单次任务 | 整个会话生命周期 |
| **生命周期** | 任务完成后终止 | 永不主动终止，直到会话过期 |
| **事件类型** | 任务进度事件 | 对话/Agent/质量/预览等 10 种事件 |
| **前端连接** | 每次任务新开连接 | 一个 EventSource 长连接保持整个会话 |
| **持久化** | 写入 SessionManager task_progress | 写入 conversation_history + recent_events |
| **重连恢复** | 重放最后一次 chat_response | 重放最近 20 条 + SessionManager 持久化事件 |

## 2. 架构设计

### 2.1 订阅者模式

SessionStreamer 采用**类级别的订阅者模式**——所有事件通过类方法推送，所有连接实例通过实例方法订阅：

```
类级别状态（跨所有连接共享）:
  _subscribers: Dict[session_id, Set[asyncio.Queue]]
  _recent_messages: Dict[session_id, List[SessionMessage]]  ← 重放缓冲
  _last_agent_msg_times: Dict[session_id, float]            ← 节流控制

推送流程:
  push_*() 类方法
    → _notify_subscribers(session_id, event_type, data)
      → 遍历 session_id 对应的所有 Queue
        → queue.put_nowait(message)

消费流程:
  SessionStreamer(session_id) 实例
    → subscribe()       注册自己的 Queue 到 _subscribers[session_id]
    → generate()         `while True: queue.get() → yield SSE`
    → unsubscribe()     断开时从 _subscribers 移除
```

### 2.2 双流架构

系统同时运行两条独立的 SSE 通道：

```
前端
├── EventSource /api/v1/stream/{task_id}
│   └── ProgressStreamer — 任务级进度（完成即终止）
│
└── EventSource /api/v1/session-stream/{session_id}   ← 本章焦点
    └── SessionStreamer — 会话级持久流（永不终止）
```

两条流在 `ProgressStreamer.push_chat_response()` 中通过**双写**机制协同：
`ProgressStreamer` 收到 chat_response 后，同时调用 `SessionStreamer.push_chat_response()` 写入持久流，确保刷新页面后消息不丢失。

### 2.3 消息格式

每条消息封装为 `SessionMessage` dataclass，序列化为标准 SSE 格式：

```
event: chat_response
data: {"session_id": "abc", "message": "...", "action": "continue_chat", ...}

event: heartbeat
data: {"session_id": "abc", "timestamp": "2026-07-07T10:00:00"}
```

SSE 协议要求每条消息以 `\n\n` 结尾，`data:` 字段为 JSON 字符串。

## 3. 事件体系

### 3.1 事件类型总览

| 事件 | 事件名 | 触发时机 | 是否持久化 | 是否进 replay buffer |
|------|--------|----------|-----------|-------------------|
| 对话回复 | `chat_response` | LLM 回复完成 | 是 (conversation_history) | 是 |
| 对话 Token | `chat_token` | LLM 逐 token 输出 | 否 | **否**（绕过） |
| 思维链 Token | `chat_thinking` | LLM 思维链输出 | 否 | **否**（绕过） |
| Agent 消息 | `agent_message` | Agent 执行进度 | 是 (conversation_history) | 是 |
| 心跳 | `heartbeat` | 每 30s 无事件 | 否 | 否 |
| 连接确认 | `connected` | 新订阅建立 | 否 | 否 |
| 质检结果 | `quality_result` | 报告质量检查完成 | 是 | 是 |
| 章节质检 | `section_quality` | 单章节质量检查 | 是 | 是 |
| 预览刷新 | `preview_refresh` | 报告预览更新 | 是 | 是 |
| 质量确认 | `quality_confirmed` | 最终质量确认 | 是 | 是 |

### 3.2 对话事件

#### `chat_response`

完整的 LLM 回复。数据载荷：

```python
{
    "session_id": str,
    "message": str,              # LLM 回复文本
    "action": str,               # continue_chat / handoff / complete
    "topic": Optional[str],      # 当前话题
    "directions": List[str],     # 建议方向
    "suggestions": List[str],    # 建议追问
    "thinking_content": Optional[str],  # LLM 思维链（仅深度模式）
    "mode": str,                 # chat / deep_research
    "step": int,                 # 当前步骤编号
    "timestamp": str,            # ISO 时间戳
}
```

持久化行为：
- 写入 `SessionManager[session_id].conversation_history`（role="assistant"）
- 同时写入 `recent_events`（事件缓冲，最多 100 条，优先保留 chat_response）

#### `chat_token` / `chat_thinking`

单 token 粒度的流式输出。设计要点：

- **绕过 `_notify_subscribers()`**：直接遍历 subscriber 队列推送，不进入 `_recent_messages` 缓冲（避免堆积数万 token）
- **不持久化**：token 是瞬时状态，不写入磁盘
- **前端拼接**：前端 EventSource listener 逐 token 追加到对话气泡

```python
# chat_token 数据格式
{"session_id": str, "token": str}

# chat_thinking 数据格式
{"session_id": str, "token": str}
```

### 3.3 Agent 消息事件

#### `agent_message`

Agent 执行过程中的进度更新。数据载荷：

```python
{
    "session_id": str,
    "agent_id": str,          # 如 "researcher", "analyst"
    "agent_name": str,        # 可读名称
    "action": str,            # searching / analyzing / completed / asking / ...
    "content": str,           # 可读描述
    "timestamp": str,
}
```

**节流机制**：同一 session 的 agent_message 推送间隔不低于 200ms（`_AGENT_MSG_THROTTLE_SECONDS`），避免 Agent 密集状态变更导致前端过载。心跳类动作（action="heartbeat"）不受节流限制。

**特殊用途**：`push_clarification()` 复用 agent_message 通道，以 agent_id="clarifier" 的格式推送澄清问题，前端通过 clarification_id 识别并弹出输入框。

持久化行为：
- 写入 `conversation_history`（role="agent"，含 agent_id/agent_name/action）
- 200ms 节流仅作用于 SSE 推送，持久化不受节流影响

### 3.4 质量事件

#### `quality_result`

质量检查完成后的汇总结果。数据载荷：

```python
{
    "session_id": str,
    "overall_score": float,         # 0-100
    "overall_status": str,          # passed / warning / failed
    "section_results": Dict,        # {section_name: {score, issues, ...}}
    "issues": List[Dict],           # 最多 20 条
    "timestamp": str,
}
```

#### `section_quality`

单章节质量检查的增量结果：

```python
{
    "session_id": str,
    "section_name": str,
    "data": Dict,                   # 该章节的完整检查数据
}
```

支持**增量更新**——质检 Agent 每完成一个章节即推送，前端逐步渲染检查结果，无需等待全文完成。

### 3.5 预览事件

#### `preview_refresh`

报告 HTML 预览就绪时触发。数据载荷：

```python
{
    "session_id": str,
    "preview_url": str,         # /api/v1/preview/{session_id}
    "version_id": str,          # 版本标识
    "timestamp": str,
}
```

前端收到后刷新 iframe 或导航到预览页面。

#### `quality_confirmed`

用户最终确认质量时触发：

```python
{
    "session_id": str,
    "final_document_path": str,  # 最终文件路径
    "timestamp": str,
}
```

### 3.6 连接维护事件

#### `connected`

新订阅建立时的确认事件。前端应监听此事件确认连接成功：

```python
{
    "session_id": str,
    "timestamp": str,
}
```

#### `heartbeat`

每 30 秒空闲期内自动发送，保持连接不超时。前端无需特殊处理，浏览器 EventSource API 会自动维护连接。Nginx 等反向代理的 proxy_read_timeout 应设置为大于 30 秒。

## 4. 重放与持久化机制

### 4.1 重放缓冲（内存级）

```
最近 20 条事件 → _recent_messages[session_id] → List[SessionMessage]

写入: push_*() 的 _notify_subscribers() 自动追加
限制: _MAX_REPLAY = 20（FIFO，超出舍去最旧）
绕过: chat_token / chat_thinking（避免 token 淹没缓冲）
```

### 4.2 持久化事件（磁盘级）

```
SessionManager.recent_events → List[Dict]
  限制: 最多 100 条
  优先级: chat_response 优先保留，agent_message 裁减

SessionManager.conversation_history → List[Dict]
  写入: chat_response（role=assistant）、agent_message（role=agent）
  用途: 页面刷新后完整恢复对话上下文
```

### 4.3 订阅时的恢复顺序

```
subscribe()
  │
  ├─ 1. 从 _recent_messages 重放 (内存缓冲，即时)
  │
  ├─ 2. 如果内存缓冲为空，从 SessionManager.recent_events 加载
  │      (页面刷新/服务重启后恢复)
  │
  └─ 3. 重放入口 Queue → generate() → SSE → 前端
```

此机制确保：
- **断开重连**（短时间）：从内存缓冲恢复，零延迟
- **页面刷新**（长时间）：从 SessionManager 持久化事件恢复
- **首次连接**：缓冲为空，等待新事件

## 5. 生命周期

### 5.1 状态图

```
               新前端连接
                  │
                  ▼
  ┌──────────────────────────────┐
  │          subscribe()         │
  │  创建 Queue → 注册到类级别   │
  │  重放缓冲 → 发送 connected   │
  └──────────┬───────────────────┘
             │
             ▼
  ┌──────────────────────────────┐
  │          generate()          │
  │  ┌────────────────────────┐  │
  │  │  while True:           │  │
  │  │    await queue.get()   │  │
  │  │    30s 超时→heartbeat  │  │
  │  │    yield SSE           │  │
  │  └────────────────────────┘  │
  └──────────┬───────────────────┘
             │
   前端断开 / CancelledError
             │
             ▼
  ┌──────────────────────────────┐
  │         unsubscribe()        │
  │  从 _subscribers 移除 Queue  │
  │  清理空 session 的缓冲       │
  └──────────────────────────────┘
```

### 5.2 关键设计决策

- **永不主动终止**：generate() 的 `while True` 仅在 `CancelledError` 或异常时退出
- **资源清理**：当某个 session 的所有 subscriber 都断开后，删除 `_subscribers[session_id]` 和 `_recent_messages[session_id]`
- **重连安全**：subscribe() 总是创建新 Queue，旧 Queue 在 unsubscribe() 时被丢弃，不影响新连接

## 7. 与 SessionManager 的协作

SessionStreamer 与 SessionManager 的协作是**双向的**：

### SessionStreamer → SessionManager（写入）

```
push_*()
  → _persist_event()
    → SessionManager.get_instance().get(session_id)
      → session["conversation_history"].append(...)  (chat/agent消息)
      → session["recent_events"].append(...)          (所有事件，最多100条)
        → SessionManager 自动持久化到磁盘 (tmp+rename原子写入)
```

`_persist_event()` 捕获所有异常，持久化失败不影响 SSE 推送（fail-open 设计）。

### SessionManager → SessionStreamer（重放）

```
subscribe()
  → _recent_messages 为空时
    → SessionManager.get_instance().get(session_id)
      → session["recent_events"] → 重建 SessionMessage → 写入 Queue
```

### 协同效果

| 场景 | SessionStreamer | SessionManager |
|------|----------------|----------------|
| 正常推送 | SSE → 前端 | 写入 conversation_history |
| 前端刷新 | 从内存缓冲重放（即时） | 从 recent_events 恢复（后备） |
| 服务重启 | 缓冲丢失 | 从磁盘 JSON 文件恢复 |
| 消息回滚 | — | WAL + 原子写入确保一致性 |

## 8. 性能设计

### 8.1 节流控制

| 机制 | 参数 | 说明 |
|------|------|------|
| agent_message 节流 | 200ms | 同 session 的 agent_message 最短间隔 |
| chat_token 绕过缓冲 | — | 不进入 _recent_messages 避免 OOM |
| chat_thinking 绕过缓冲 | — | 同上 |
| 心跳超时 | 30s | 无事件时自动 heartbeat |

### 8.2 缓冲管理

| 缓冲 | 大小 | 回收策略 |
|------|------|---------|
| _recent_messages | 最多 20 条/session | 订阅者全断开时清除 |
| SessionManager.recent_events | 最多 100 条/session | 超出时裁减 agent_message |
| SessionManager.conversation_history | 无硬限制 | 依赖 HistoryCompressor 三层压缩 |

### 8.3 异常安全

| 异常类型 | 处理方式 |
|---------|---------|
| QueueFull | 日志警告，丢掉事件（不影响后续推送） |
| 队列消费者异常 | 加入 dead_queues，unsubscribe 时清理 |
| _persist_event 失败 | 捕获异常，仅 debug 日志（SSE 推送不受影响） |
| CancelledError | 正常退出 generate()，执行 unsubscribe() |
| 未预期异常 | error 日志 + exc_info，finally 保证 unsubscribe() |

## 9. 对比：SessionStreamer vs ProgressStreamer

| 维度 | SessionStreamer | ProgressStreamer |
|------|----------------|-----------------|
| **作用域** | 会话级 | 任务级 |
| **生命周期** | 整个会话（永不主动终止） | 任务完成/失败后终止 |
| **前端连接数** | 每个会话 1 个长连接 | 每个任务 1 个短连接 |
| **事件类型** | 10 种（对话+Agent+质量+预览） | 任务阶段/进度/日志 |
| **持久化** | conversation_history + recent_events | task_progress + task_phases |
| **重放** | 内存 20 条 + SessionManager 100 条 | 最后一次 chat_response |
| **终止条件** | 前端断开 / CancelledError | 任务完成/失败 / 超时 |
| **心跳** | 30s heartbeat（保活） | 无（主动终止） |
| **资源清理** | 全部 subscriber 断开后清理 session | 状态 TTL 300s 后清理 |
| **前端 API** | `EventSource(/api/v1/session-stream/{sid})` | `EventSource(/api/v1/stream/{tid})` |

## 10. 故障排除

### 10.1 前端收不到事件

1. 确认前端连接的是 `/api/v1/session-stream/{session_id}`（而非 `/stream/`）
2. 检查后端日志 `No session subscribers for {id}` — 表明事件推送时前端尚未连接
3. 确认 Nginx proxy_read_timeout > 30s，否则心跳被截断
4. 检查浏览器 EventSource `onerror` 回调是否被触发

### 10.2 重连后丢失消息

1. 检查 `_persist_event()` 是否成功调用（debug 日志 `Failed to persist event`）
2. 检查 SessionManager 文件写权限
3. 确认事件在 `recent_events` 的 100 条限制内未被裁减

### 10.3 服务重启后会话恢复

1. SessionManager 从磁盘加载会话 JSON
2. subscribe() 时 `_recent_messages` 为空（内存丢失）
3. 自动从 `SessionManager.recent_events` 加载
4. 如果 `recent_events` 为空，则 conversation_history 至少保留了对话消息
