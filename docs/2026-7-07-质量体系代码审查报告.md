### 2.1 认知防御体系 L2 策略引擎未实现，L3 为 Prompt 注入无强制验证

### 2.2 SharedMemory 存在绕过 canonical 质检的同步写入路径

**文件**: `src/core/communication.py:155-164`, `src/core/orchestrator/execution/engine.py:1471-1473`

`write_canonical()` 是唯一提供冲突检测、版本控制、事件发布的写入入口。但存在其他写入路径：

1. **`SharedMemory.write()`** (line 155-164, async): 无版本控制、无冲突检测、无事件发布
2. **`SharedMemory.set()` / `set_all()`** (line 335-365, sync): 标注了"非线程安全"，绕过锁和版本管理
3. **引擎批量注入** (`engine.py:1471-1473`):
   ```python
   self._shared_memory.set("_canonical_registry", self._active_canonical_data)
   ```
   整批写入 canonical registry，完全绕过 `write_canonical()` 的质检逻辑

`set()` 和 `write()` 是同步/轻量级存取方法，设计上不承诺质量管控。风险在于：调用者可能在不知情的情况下通过这些路径写入应受管控的数据。

**影响范围**: 通过非 canonical 路径写入的数据不受版本控制、冲突检测和事件通知保护。
**建议**: 为同步路径写入 canonical 前缀的数据时记录告警日志，或禁止非 canonical 路径写入以 `canonical:` 为前缀的 key。

## 3. 逻辑缺陷

### 3.1 write_canonical() 参数命名混淆引发未来风险

**文件**: `src/core/communication.py:233`

```python
# caliber 字段实际存储的是 SOURCE_PRIORITY 的 key
existing_priority = SOURCE_PRIORITY.get(existing.get("caliber", ""), 0)
new_priority = SOURCE_PRIORITY.get(caliber, 0)
```

实际运行的调用链（generic_agent.py:470/578/892/903-906）**全部**传递的是 `SOURCE_PRIORITY` 的 key 值（`caliber="structured_source"`、`caliber="search_result"`、`caliber="llm_inference"` 等），因此当前运行中**没有实际数据损坏**。仅在 caliber 被误传为口径值（如"归母"）时才会出问题。

但参数命名严重不当：
- 参数名 `caliber` 在语义上表示数据口径（归母/扣非/GAAP）
- 实际存储的是**来源类型标识符**（应命名为 `provenance` 或 `source_type`）
- 无输入校验：若传入口径值，`SOURCE_PRIORITY.get("归母", 0)` 返回 0
- `communication.py:204` 的 TODO 注释暗示此参数原设计承载 caliber 语义，但被混用

**影响范围**: 当前运行安全（按约定正确），命名混淆可能在未来引入 bug。
**建议**: 重命名参数为 `source_type`，或增加 `SOURCE_PRIORITY` 校验。

### 3.2 _check_caliber_coverage() 评分公式失效

**文件**: `src/core/quality/checkers.py:445-452`

```python
ratio = caliber_refs / max(1, len(numeric_refs) * 0.3)
# 分母压缩到 30%，ratio 极易 >= 1.0
```

分母乘以 0.3（将有效数值引用数压缩到 30%），导致 ratio 极易达到 1.0 以上：

| numeric_refs | caliber_refs | ratio | score |
|-------------|-------------|-------|-------|
| 1 | 1 | 3.33 | 100 |
| 2 | 1 | 1.67 | 100 |
| 3 | 1 | 1.11 | 100 |
| 4 | 1 | 0.83 | 83 |
| 10 | 1 | 0.33 | 33 |
| 10 | 3 | 1.00 | 100 |

当数值引用数 <= 3 时，**任意一个**口径关键词匹配即得满分。只有报告中含 4+ 数值引用且口径匹配极少时，分数才会下降到阈值以下。口径覆盖率指标形同虚设。

**触发频率**: 多数短报告中口径覆盖率出错但显示 100 分，误导用户认为口径标注充分。
**修复**: 改为 `ratio = caliber_refs / max(1, len(numeric_refs))`，0.7 表示 70% 的数据点有口径标注。

### 3.3 搜索质量过滤的中文相关度退化

**文件**: `src/core/search_quality_filter.py:418-421`

CJK 字符被逐字分割加入 query terms：

```python
if '\u4e00' <= ch <= '\u9fff':
    terms.append(ch)  # 单个汉字作为独立 term
```

任何含"的"、"了"、"是"、"在"等高频字的页面都获得匹配加分，相关度评分被稀释。

**问题**: 
- 高频停用词污染匹配信号
- 无法区分"市场规模"和"场的规模"（相同字符集不同语义）
- 长 query 中无关字符匹配概率高

**修复**: 引入 jieba 分词 + 停用词过滤。

### 3.4 日期解析仅 3 种格式

**文件**: `src/core/search_quality_filter.py:499-538`

```python
_DATE_FORMATS = ["%Y-%m-%d", "%Y/%m/%d", "%Y年%m月%d日"]
```

**修复**: 用 `dateutil.parser` 或扩充到 10 种格式。

### 3.5 L5 矛盾检测 LLM 不可用时的假阳性

**文件**: `src/core/agents/generic_agent.py:2123`

```python
# LLM 调用失败时回退
return f"方向矛盾(启发式): '{stmt_a[:50]}' vs '{stmt_b[:50]}'"
```

LLM 不可用时，每个通过预检的 pair 都被直接报告为矛盾。**这是确保的假阳性**。

**对比**: 
- LLM 成功时：需要 `confidence >= 0.6` 才确认矛盾
- LLM 失败时：不经过任何置信度过滤，直接报告

**建议**: LLM 不可用时返回 `None`（不报告），或至少降低回退的严重等级为 warning 而非 confirmed contradiction。

### 3.6 L5 预检过度敏感

**文件**: `src/core/agents/generic_agent.py:2063`

```python
if overlap > 0.15:
    return True
```

Bigram 重叠阈值 0.15 意味着两句话共享约 15% 的共现字符对就可能触发。此值过低，导致大量非矛盾 pair 进入 LLM 阶段浪费 token。

**示例**:
- "营收增长主要来自线上渠道" vs "营收增长主要来自线下渠道"
- 共享 bigram："营收"、"收增"、"增长"、"长主"、"主要" → 重叠远高于 0.15

**建议**: 提高至 0.25-0.30，或在预检中引入实体对齐（确认两个 claim 讨论同一主体）。

### 3.9 assessment_driven 认知策略参数与设计文档不一致

**文件**: `src/core/agents/generic_agent.py:110-116`

**设计文档**: `docs/superpowers/specs/2026-07-01-aspect-cognitive-strategy-design.md` v1.3

`COGNITIVE_STRATEGY["assessment_driven"]` 中有 10 处参数值与设计文档不一致：

| 层 | 参数 | 设计文档值 | 代码实际值 | 位置 |
|----|------|-----------|-----------|------|
| L1 | `dimension_ceiling` | `"inferential"` | `None` | `:111` |
| L1 | `speculative_word_downgrade` | `"strict"` | `"relaxed"` | `:111` |
| L1 | `confidence_threshold` | `{"factual": "HIGH", "inferential": "HIGH"}` | `{"factual": "HIGH", "inferential": "MEDIUM", "speculative": "LOW"}` | `:111` |
| L2 | `same_caliber_resolution` | `"more_precise_data"` | `"wider_coverage"` | `:112` |
| L2 | `speculative_write_policy` | `"with_confidence_interval"` | `"with_falsification_condition"` | `:112` |
| L3 | `speculative_policy` | `"reference_only"` | `"open_use"` | `:113` |
| L3 | `reasoning_mode` | `"sensitivity_analysis"` | `"risk_scenario"` | `:113` |
| L4 | `hypothesis_count` | `(2, 3)` | `(1, 2)` | `:114` |
| L4 | `agent_hypothesis_count` | `1+` | `0` | `:114` |
| L4 | `counter_hypothesis_required` | `True` | `False` | `:114` |

L1 的 3 处偏差影响最严重：`dimension_ceiling=None` 意味着 assessment_driven 维度可以产出 speculative 级别的 claim（设计意图是封顶在 inferential）；`speculative_word_downgrade="relaxed"` 允许推测性措辞保留原始级别（设计意图是严格降级）；`confidence_threshold` 缺少 `inferential: "HIGH"` 导致推断性 claim 只需 MEDIUM 置信度即可通过（设计意图是量化推断需高置信度），且代码多了设计文档未定义的 `speculative: "LOW"` 键。

由于 L2 策略引擎未实现，L2 的 2 处偏差当前无运行时影响。但 L3 的 2 处偏差影响显著：`speculative_policy="open_use"` 允许 assessment_driven 维度将推测性 claim 直接作为结论基础（设计意图 `reference_only` 要求仅作方向参考）；`reasoning_mode="risk_scenario"` 使推理方向偏向"风险情景"而非设计意图的"敏感性分析"。L4 的 3 处偏差直接控制假设生成行为：assessment_driven 维度当前不生成 agent 自有假设（`agent_hypothesis_count=0`），而设计意图要求至少 1 个；`counter_hypothesis_required=False` 不要求反面假设（设计意图要求必须有），且 `hypothesis_count=(1,2)` 少于设计意图的 `(2,3)`。

**影响范围**: assessment_driven 类型的维度（估值分析、风险分析等）分析行为与设计意图偏离。
**建议**: 对齐设计文档，或将设计文档更新为代码实际值并记录变更原因。

### 3.10 get_canonical_sync 前缀匹配过宽导致误读

**文件**: `src/core/communication.py:299-304`

```python
prefix = metric.split("_")[0]
for key, value in self._data.items():
    if key.startswith("canonical:"):
        key_metric = key[len("canonical:"):]
        if key_metric == metric or key_metric.split("_")[0] == prefix:
            return value
```

当精确匹配失败时，回退为按 `_` 分割取前缀匹配。这导致：

| 查询 metric | 匹配到的 key | 是否正确 |
|------------|-------------|---------|
| `净利润_2024` | `canonical:净利润_2024` | ✅ |
| `净利润_2025`（不存在） | `canonical:净利润_2024` | ❌ 返回 2024 数据 |
| `营收_2024` | `canonical:营收_2024` | ✅ |
| `营收`（不存在） | `canonical:营收_2024` 或 `canonical:营收_2025`（第一个遍历到） | ❌ 不确定年份 |

此方法用于 Prompt 构建上下文（同步读取），错误数据注入分析 Prompt 会产生基于错误年份的推理。

**影响范围**: 任何通过 `get_canonical_sync` 读取的 metric 若不存在精确匹配，可能返回不同年份/口径的数据。
**建议**: 移除前缀回退逻辑，精确匹配失败时返回 `None`；或改为模糊匹配时记录告警日志。

## 4. 架构缺失

### 4.1 引擎质量门禁是软的

**文件**: `src/core/orchestrator/execution/engine.py:1591-1593`

```python
# 即使重试耗尽，执行仍继续
batch_results = _current_batch  # 使用合并但可能不合格的结果
```

质量检查失败 → 重试 → 重试耗尽 → 仍然使用不合格结果继续执行。唯一的硬中止条件：批次内**所有** Agent 全部失败（line 1602-1607）。

### 4.3 无跨 Agent 批量数据对账

`ReportQualityChecker._check_cross_chapter_consistency()` 仅在最终报告阶段执行跨章节数据比对。分析阶段跨 Agent 的数据一致性完全依赖 `SharedMemory.write_canonical()` 的冲突检测机制，该机制仅在偏差 >5% 时标记冲突，且不产生阶段报告。

**缺失的对账场景**:
- 批次 A 中 Agent1 写 "营收=100亿" → 批次 B 中 Agent2 读到此值
- Agent2 基于此值推理，产生结论 X
- 批次 C 补充搜索后写入 "营收=95亿"（偏差 5%，恰好低于阈值，无冲突标记）
- Agent2 的结论 X 基于旧值，未被重新评估
- 最终报告时才发现跨章节数据不一致，但修复窗口已关闭

**建议**: 在批次汇总后、合成步骤前增加跨 Agent 数据对账。
